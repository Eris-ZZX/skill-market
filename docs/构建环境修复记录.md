## 问题 1：crates.io 直连卡死

### 症状

`cargo fetch` / `cargo check` 长时间无输出，CPU 几乎不增长（1–2 秒），`registry/index` 目录始终为空，`.crate` 文件数不增长。

单文件 `Invoke-WebRequest https://static.crates.io/...` 下载正常（77KB/1.3s），但 cargo 并发多连接时挂起。

### 修复

⚠️ **注意 `CARGO_HOME` 的位置**。本机是 `D:\Dev\rust\.cargo`，**不是** `~/.cargo`。配置必须写在 `$env:CARGO_HOME\config.toml`。

```toml
# D:\Dev\rust\.cargo\config.toml
[source.crates-io]
replace-with = 'rsproxy-sparse'

[source.rsproxy-sparse]
registry = "sparse+https://rsproxy.cn/index/"

[registries.rsproxy]
index = "https://rsproxy.cn/crates.io-index"

[http]
# 国内网络下 HTTP/2 多路复用常导致连接挂起
multiplexing = false
timeout = 60
low-speed-limit = 10

[net]
git-fetch-with-cli = true
retry = 5
```

### 验证

首次 `cargo fetch` 约 10 分钟（含 Rust 工具链 + 760 个 crate），最终 `exit_code: 0`，缓存 759/760。

## 问题 2：`rust-toolchain.toml` 版本锁定

### 症状

```
error: error calling dlltool 'dlltool.exe': program not found
error: could not compile `getrandom` (lib)
```

### 根因

上游 `rust-toolchain.toml` 写的是 `channel = "1.95"`。rustup 解析时**按 host 推断变体**，这台机器的 rustup 环境被推断成 `x86_64-pc-windows-**gnu**`：

```
$ rustc -vV
host: x86_64-pc-windows-gnu
```

于是自动下载 `1.95-x86_64-pc-windows-gnu`，它需要 MinGW 的 `dlltool.exe`，但本机只有 MSVC 工具链。

### 尝试过的无效修复

| 尝试 | 结果 |
|---|---|
| `channel = "1.95-x86_64-pc-windows-msvc"` | ❌ `error: target tuple in channel name`（rustup 不接受在 channel 里写 target） |
| `channel = "1.95"` + `targets = [...]` | ❌ 仍推断为 gnu |

### 有效修复

**绕过版本锁定**（当前采用）：

```powershell
cd <repo>
Move-Item rust-toolchain.toml rust-toolchain.toml.bak
```

默认工具链是 `stable-x86_64-pc-windows-msvc`（1.96.0），host 正确。

**长期方案**（未采用，因为改全局会影响其他项目）：

```powershell
rustup set default-host x86_64-pc-windows-msvc
rustup toolchain install 1.95.0-x86_64-pc-windows-msvc -c rustfmt -c clippy
rustup override set 1.95.0-x86_64-pc-windows-msvc
```

> `1.95` 和 `1.95.0` 在 rustup 里语义不同：前者是 channel 名（可推断变体），后者是具体版本号。

## 问题 3 & 4：`aws-lc-sys` —— 最终解法是移除

### 症状演进

一开始是链接错误：

```
chacha-x86_64.obj : fatal error LNK1107: 文件无效或损坏: 无法在 0x4000 处读取
```

改源码编译后变成解析错误：

```
chacha-x86_64.asm:1: error: label or instruction expected at start of line
```

### 真正的根因（问题 4）

检查源文件头，发现是**加密过的**：

```
%TSD-Header-###%$...（二进制乱码）
```

- 全仓 718 个 `.c` / `.h` / `.asm` 文件中，**恰好 39 个 `.asm` 全部损坏**
- `.crate` 原始包是正常的 gzip（`1f 8b`）
- 从 `.crate` 重新解压到 TEMP 得到正常内容（`; This file is g...`）
- **但一旦复制这个文件（哪怕改扩展名为 `.bak`），立即被重新加密**
- 新建的空 `.asm` 文件不会被加密

**结论：公司 DLP 系统按文件内容哈希拦截 `aws-lc` 的汇编文件**（它们包含加密算法实现）。这是安全策略，技术上无法绕过，**也不应该绕过**。

### 正确解法：移除 `aws-lc-rs`，改用 `ring`

`ring` 是纯 Rust/C 实现，不含 NASM 汇编，不会被拦截。

`aws-lc-rs` 的引入路径有三处，逐一掐断：

#### ① 移除 `tauri-plugin-updater`

内网本来就用不上它（更新源指向公网），且它通过 `reqwest 0.13` + `rustls-platform-verifier` 强制引入 aws-lc。

```toml
# Cargo.toml —— 删除这一行
- tauri-plugin-updater = "2"
```

删除代码：
- `src/commands/settings.rs`：`use tauri_plugin_updater::UpdaterExt;`、`UpdateDownloadProgress` 结构体、`install_update_and_restart()`、`check_app_update_available()` 两个函数
- `src/lib.rs`：`.plugin(tauri_plugin_updater::Builder::new().build())` 及 `invoke_handler` 里的两条命令注册
- `capabilities/default.json`：`"updater:default"` 权限

#### ② `hyper-rustls` 关掉 default

**关键坑**：只加 `ring` 不够，`default` feature 里含 `aws-lc-rs`。

```toml
# ❌ 这样写 aws-lc 还在
hyper-rustls = { version = "0.27", features = ["http1", "tls12", "ring", "webpki-tokio"] }

# ✅ 必须 default-features = false
hyper-rustls = { version = "0.27", default-features = false, features = ["http1", "http2", "tls12", "ring", "webpki-tokio", "native-tokio"] }
```

#### ③ `tokio-rustls` 同样关掉 default

```toml
# ❌
tokio-rustls = "0.26"

# ✅
tokio-rustls = { version = "0.26", default-features = false, features = ["tls12", "ring", "logging"] }
```

#### ④ `reqwest` 用 no-provider + `rustls` 显式指定 ring

```toml
reqwest = { version = "0.12", default-features = false, features = ["json", "stream", "socks", "charset", "http2", "rustls-tls-native-roots-no-provider"] }

rustls = { version = "0.23", default-features = false, features = ["ring", "std", "tls12", "logging"] }
```

> `rustls-tls-native-roots-no-provider` 保留系统根证书链（内网自签/企业代理必需），但不指定加密提供者，由 `rustls` 的 `ring` feature 决定。

### 验证

```powershell
cargo tree -i aws-lc-rs
# error: package ID specification `aws-lc-rs` did not match any packages
```

包彻底消失。`cargo check` 输出里 `aws-lc` 出现 **0 次**。

## 附：CMake / NASM 的安装（备用）

即便最终没用到 CMake 编译 aws-lc，记录一下当时有效的安装方式，以备将来需要编译其他 C 依赖。

### CMake —— 用 PyPI 的 wheel（最快）

`cmake.org` 直连只有 50KB/s，`winget` 走 GitHub releases 同样慢。**PyPI 腾讯镜像 2.3MB/s**：

```powershell
python -m pip install cmake -i https://mirrors.cloud.tencent.com/pypi/simple/ --trusted-host mirrors.cloud.tencent.com
```

可执行文件位置：

```
C:\Users\<user>\AppData\Local\Python\pythoncore-3.14-64\Lib\site-packages\cmake\data\bin\cmake.exe
```

### NASM —— 官方源可直接下

```powershell
$zip="$env:TEMP\nasm.zip"
Invoke-WebRequest "https://www.nasm.us/pub/nasm/releasebuilds/2.16.03/win64/nasm-2.16.03-win64.zip" -OutFile $zip
Expand-Archive $zip -DestinationPath "$env:LOCALAPPDATA\nasm-portable" -Force
```

> ⚠️ 不要用 `pip install nasm` —— PyPI 上那个包是无关库（0.1.0 版，import 就报错）。
> ⚠️ `winget install NASM.NASM` 会显示"已成功安装"但实际没装上，且 `winget list` 查不到。

### Ninja

```powershell
python -m pip install ninja
# 可执行文件：C:\Users\<user>\AppData\Local\Python\pythoncore-3.14-64\Scripts\ninja.exe
```

## 构建脚本

`build-msvc.cmd`（放在仓库根）：

```cmd
@echo off
REM 在 MSVC 环境下执行 cargo
REM 本机 VS 未在 Installer 注册，CMake 的 VS 生成器找不到实例，
REM 故用 vcvars64 + Ninja（若将来需要编译 C 依赖）

set VCVARS_VER=-vcvars_ver=14.44
if not exist "D:\VS\main\VC\Tools\MSVC\14.44.35207" set VCVARS_VER=

call "D:\VS\main\VC\Auxiliary\Build\vcvars64.bat" %VCVARS_VER% >nul 2>&1
if errorlevel 1 ( echo [ERROR] vcvars64.bat failed & exit /b 1 )

set CMAKE_BIN=C:\Users\%USERNAME%\AppData\Local\Python\pythoncore-3.14-64\Lib\site-packages\cmake\data\bin
set NINJA_BIN=C:\Users\%USERNAME%\AppData\Local\Python\pythoncore-3.14-64\Scripts
set NASM_DIR=C:\Users\%USERNAME%\AppData\Local\nasm-portable\nasm-2.16.03
set PATH=%CMAKE_BIN%;%NINJA_BIN%;%NASM_DIR%;%PATH%

if exist "C:\ck" ( set CARGO_TARGET_DIR=C:\ck )

cd /d "%~dp0src-tauri"
cargo %*
```

> 移除 aws-lc 后，其实**直接用普通 `cargo build` 也行**（不再需要 vcvars / cmake / nasm）。这个脚本保留是为了将来引入其他 C 依赖时备用。
