## 三、P0：补齐功能闭环

### P0-1 更新技能（最关键）

**问题**：现在能识别「可更新」，但没有执行入口。用户在界面上看到蓝标却点不动。

**要做的**：

```
新增 update_skill 命令
  ├─ 下载新版本到临时目录
  ├─ 判断本地是否被改过（严格哈希）
  │   ├─ 未改 → 直接替换
  │   ├─ 已改 → 拒绝，提示「本地有改动」
  │   └─ 冲突 → 弹三选一（留我的/用远端/另存）
  ├─ 备份旧版本到 snapshots（复用发布快照机制）
  ├─ 原子替换：先写 .new 目录，成功后 rename
  └─ 更新 state.json 的 installedHash / installedVersion
```

**难点**：Windows 上目录 rename 需要目标不存在，必须先删再改名，中间有窗口期。要么用 `MoveFileEx` 的 `MOVEFILE_REPLACE_EXISTING`，要么接受短暂不一致。

**预估**：1.5 人日

**验证标准**：
- [ ] 改一版技能推到 GitLab → 点「检查更新」看到蓝标
- [ ] 点更新 → 文件真的变了
- [ ] 本地改过再点更新 → 被拒绝并有明确提示

---

### P0-2 冲突处理三选一

**问题**：`ConflictChoice` 枚举定义了但没用上。

**要做的**：

```
留我的    → 不动本地，记录「忽略此次更新」，远端再变时重新提示
用远端    → 备份本地到 snapshots 后覆盖
另存一份  → 本地改名 <name>-local，再装新版 <name>
```

**预估**：0.5 人日（依赖 P0-1）

---

### P0-3 补充 LICENSE

MIT，与 README 声明一致。

**预估**：5 分钟

## 四、P1：日常可用性

### P1-1 未管理技能扫描

**问题**：用户机器上已存在的技能（cc-switch 装的、手放的）完全看不到。

**实测依据**：本机 `~/.agents/skills` 有 44 个技能，其中 28 个与 cc-switch 的库重复，16 个是独立的。不扫描就等于假装它们不存在。

**要做的**：

```
新增 scan_unmanaged 命令
  ├─ 遍历六个工具的技能目录
  ├─ 排除 state.json 里已记录的
  ├─ 解析每个 SKILL.md 拿 name/description
  └─ 返回「本地已有，非本工具安装」列表
```

界面：「我的技能」页加一个分栏或标签页。

**约束**：**只读，不接管、不删除**。用户可以选择「导入到我的库」。

**预估**：0.5 人日

---

### P1-2 junction 模式接上前端

**问题**：`junction_available()` 命令存在但前端只在设置页显示状态，安装时始终用 copy。

**要做的**：

- 设置页已有「默认安装方式」字段，把它接到 `install_skill` 的参数
- 安装弹窗里显示当前模式，允许单次覆盖

**预估**：0.5 人日

---

### P1-3 技能详情显示完整 SKILL.md

**问题**：现在详情页只显示 frontmatter 解析出的描述，看不到正文。

**为什么要看正文**：安装前想确认这个技能到底做什么，是决策依据。

**要做的**：

- 新增 `get_skill_content(repo_path)` 命令，返回 SKILL.md 全文
- 前端用简易 Markdown 渲染（不用引入重型库，只需标题/列表/代码块）

**预估**：1 人日

---

### P1-4 发布流程的前端校验

**问题**：现在发布全靠后端报错，用户要等一次网络往返才知道 name 不合法。

**要做的**：

- 选目录后立即在本地解析 frontmatter，展示将提交的 name/category/version
- 实时校验 name 格式、是否与目录名一致
- 显示「这是新建」还是「这会覆盖 xxx」

**预估**：0.5 人日

---

### P1-5 客户端自更新

**问题**：现在换版本要手动重装 MSI。

**要做的**：

```
设置页加「检查新版本」
  ├─ 查 GitHub Releases（或内网 GitLab Releases）
  ├─ 有新版本 → 显示版本号 + 下载链接
  └─ 点链接用系统浏览器打开（不静默安装）
```

**注意**：本项目已移除 `tauri-plugin-updater`（它强制引入 aws-lc-rs）。所以只能做「提示 + 跳转下载」，不能自动安装。

**预估**：0.5 人日

## 五、P2：质量与可维护性

### P2-1 CI 流水线

GitHub Actions：

```yaml
on: [push, pull_request]
jobs:
  check:
    - cargo check
    - cargo test --lib
    - cargo clippy -- -D warnings
    - cargo fmt --check
    - pnpm typecheck
    - pnpm build:renderer
  e2e:
    - 仅在 PR 到 master 时，用 secrets 里的测试仓库凭据跑 ignored 测试
```

**预估**：0.5 人日

---

### P2-2 更新逻辑的端到端测试

现在 e2e 测试只覆盖「下载 + 安装」，没覆盖「更新」。

要补：
- 装 v1 → 仓库改成 v2 → 检查更新 → 更新 → 断言内容变新
- 装 v1 → 本地改文件 → 检查更新 → 断言判为「已修改」
- 装 v1 → 仓库改 + 本地改 → 断言判为「冲突」

**预估**：0.5 人日

---

### P2-3 错误文案梳理

现在的错误直接透出 `anyhow` 的 message，有些很技术化（如 `reqwest::Error { kind: Request }`）。

要做的：定义错误码枚举，前端按码映射文案。至少覆盖：
- 网络不可达 / 证书错误 / 401 / 404
- 工具未安装 / 缺 skills 目录 / 目标已存在
- 权限不足（403 on protected branch）

**预估**：0.5 人日

---

### P2-4 打包与分发

- MSI 打包验证（`webviewInstallMode: offlineInstaller` 是否生效）
- 图标替换（现在用的是 cc-switch 的）
- 版本号策略

**预估**：0.5 人日

---

### P2-5 首次启动引导

现在第一次打开是空态，用户可能不知道该干什么。

要做的：三步引导
1. 填 GitLab 地址（带「测试连接」）
2. 刷新索引
3. 装第一个技能

**预估**：0.5 人日

## 六、P3：可以不做

| 项 | 说明 |
|---|---|
| 项目级安装（`<repo>/.cursor/skills/`） | 只有需要「项目专属技能」时才要 |
| 批量操作（多选安装/卸载） | 技能少时用不上 |
| 分类管理界面 | 现在靠目录结构够了 |
| 深链（`skillmarket://install/xxx`） | 分享链接用，非必需 |
| 多仓库支持 | 单仓库够用 |
| 评分 / 下载量 | 需要服务端，与「零服务端」定位冲突 |

## 九、风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| **内置 Token 被反编译提取** | 中 | 已是 Project Token + scoped，破坏面限于「能直推 master」；配快照可回滚 |
| **Windows 目录替换的原子性** | 中 | 更新时先写 `.new` 再 rename；失败可回滚到快照 |
| **中文路径在其他 GitLab 版本表现不同** | 低 | 已用「整仓下载 + 本地切分」绕开，不依赖 path 参数 |
| **千问/WorkBuddy 回写字段导致误判** | 中 | 哈希黑名单已实现，但**未经真实环境验证**（见 P0-1 验证标准）|
| **DLP 环境对 exe 的拦截** | 中 | 需找 IT 加白名单或代码签名 |

## 十、当前不该做的事

| 不做 | 原因 |
|---|---|
| 加服务端 | 与「零服务端」定位冲突，运维成本高 |
| 引入数据库 | JSON 完全够用，SQLite 会破坏单文件分发 |
| 恢复 tauri-plugin-updater | 会重新引入 aws-lc-rs，编译不过 |
| 支持 macOS/Linux | 无实际需求，且工具路径差异大 |
| 技能市场热度/评分 | 需服务端 |
