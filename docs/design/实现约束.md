# 关键实现约束（硬规则）

> 这些不是建议，是代码里必须成立的规则。
> 每条都注明了「为什么」和「怎么验证」，改代码前先读。

---

## R1. 只写已存在的工具目录，绝不创建根文件夹

### 规则

```
✅ 允许：<已存在工具根目录>/skills/<技能名>/   ← 创建这一层
❌ 禁止：<工具根目录>/                          ← 绝不创建
❌ 禁止：~/.cursor/  ~/.qwenworkcn/  ~/.workbuddy/  ~/.agents/   ← 绝不创建
```

判定顺序：

1. 探测工具根目录（如 `~/.cursor`）**是否存在**
2. 存在 → 检查 `<根目录>/skills` 是否存在
   - 存在 → 可安装
   - 不存在 → **先问用户确认**再创建 `skills/`（个别工具首装才有此目录）
3. 根目录不存在 → 该工具显示「未安装」，**不提供安装选项**，不创建任何东西

### 为什么

1. **创建根目录等于替用户"装了一半的软件"**。空的 `~/.workbuddy/` 会让用户误以为装了 WorkBuddy，也可能干扰该工具未来的首装逻辑（有些工具首装时会检测目录是否为空来决定是否初始化）。
2. **探测式判断比配置式更可靠**。用户不需要在设置里勾"我装了哪些工具"，客户端看目录就知道。
3. 本机实测：四个工具里 `~/.cursor` / `~/.qwenworkcn` / `~/.workbuddy` / `~/.agents` 都存在，但**同事机器大概率只装了一两个**。

### 代码落点

`ToolPathTable`（对应 cc-switch 的 `get_app_skills_dir`）要拆成两个函数：

```rust
/// 只探测，不创建
fn detect_tool(tool: &ToolKind) -> ToolDetection {
    let root = tool.home_dir();
    ToolDetection {
        root_exists: root.is_dir(),
        skills_dir_exists: root.join("skills").is_dir(),
        resolved_skills_dir: root.join("skills"),
    }
}

/// 安装前调用；内部断言根目录已存在
fn prepare_target(tool: &ToolKind, confirmed_create_skills_dir: bool) -> Result<PathBuf> {
    let d = detect_tool(tool);
    if !d.root_exists {
        bail!("{} 未安装（{} 不存在）", tool.display_name(), tool.home_dir().display());
    }
    if !d.skills_dir_exists && !confirmed_create_skills_dir {
        bail!("需要创建 {}", d.resolved_skills_dir.display());
    }
    // 只创建到 skills 这一层
    fs::create_dir_all(&d.resolved_skills_dir)?;
    Ok(d.resolved_skills_dir)
}
```

**cc-switch 的现状**：`get_app_skills_dir()` 只返回路径字符串，不做存在性判断，上层直接 `create_dir_all`。**这是我们要改的地方**。

### 验证

- [ ] 在一台没装 WorkBuddy 的机器（或用 `CC_SWITCH_TEST_HOME` 指向空目录）上，WorkBuddy 应显示「未安装」且不可选
- [ ] 确认 `~/.workbuddy` 未被创建

## R2. User 目录探测：同一技能可能对应多个工具

### 规则

用户装了哪个工具，就只写哪个；都装了才都写。**不做"全选"默认**。

| 工具 | 探测标志（目录） | 目标路径 |
|---|---|---|
| Cursor | `~/.cursor` | `~/.cursor/skills` |
| Claude Code | `~/.claude` | `~/.claude/skills` |
| Codex | `~/.codex` | `~/.codex/skills` |
| ChatGPT / Agent Skills | `~/.agents` | `~/.agents/skills` |
| 千问办公 | `~/.qwenworkcn` | `~/.qwenworkcn/skills` |
| WorkBuddy | `~/.workbuddy` | `~/.workbuddy/skills` |

### 待实测项（重要歧义）

**Codex / ChatGPT 的目录归属尚未确定**：

| 证据 | 结论 |
|---|---|
| 官方文档（Codex） | 读 `$HOME/.agents/skills` |
| cc-switch 代码 | 写 `~/.codex/skills` |
| 本机实测 | **两个目录都存在、都有内容、互不链接** |

- `~/.agents/skills` — 44 个技能，0 个符号链接
- `~/.codex/skills` — 7 个技能，2 个符号链接（指向 `~/.cc-switch/skills`）

**临时方案（在验证前）**：把 Codex 和 ChatGPT 视为**两个独立目标**，各自探测、各自写入。用户装了 Codex 就写 `.codex`，装了 ChatGPT 就写 `.agents`，都装了都写。

**验证方法**（做完即可确定）：
1. 往 `~/.agents/skills` 放一个新技能（比如 `zzz-probe`，带合法 frontmatter）
2. 重启 Codex
3. 在 Codex 里输入 `$zzz-probe` 或 `/skills` 看是否列出
4. 若能列出 → `.agents` 生效；若不能 → 只认 `.codex`
5. 删掉探针技能

## R3. 干净开始，不接管已有数据

### 规则

- 首次启动**不扫描、不导入、不接管**任何已存在的技能
- 使用独立的 SSOT 目录，不复用 `~/.cc-switch/`
- 独立的数据库文件
- 如果检测到 `~/.cc-switch/` 存在，**只在设置页显示一行提示**："检测到已安装 CC Switch，其管理的技能不会被本工具接管"，不上弹窗、不做迁移引导

### 为什么

1. cc-switch 的 SSOT 里已有 40 个技能，其中 28 个来自 Git 仓库。接管意味着要重建来源元数据、处理哈希算法版本差异（它有 legacy hash 迁移逻辑）、可能互相覆盖。
2. 两套工具同时管理同一批符号链接，会互相"抢所有权"——一个卸载，另一个的目标就断了。
3. 用户明确要求"干净开始"。

### 但必须做到"看得见"

不接管 ≠ 装作不存在。**「未管理技能」视图必须有**（cc-switch 已有 `scan_unmanaged()`）：

- 扫描各工具目录，列出**不是本工具安装的**技能
- 明确标注来源："本地已有"
- 只提供「查看」和「导入到我的库」两个动作，**不提供删除**（怕误删别人的）

### 独立目录

```
%APPDATA%\SkillMarket\
├── skills\        ← SSOT，与 ~/.cc-switch/skills 完全隔离
├── state.db       ← 独立数据库
├── cache\
└── logs\
```

## R4. Cursor 的 `skills-cursor` 必须硬编码排除

### 规则

允许写入：`~/.cursor/skills/`
**绝对禁止**：`~/.cursor/skills-cursor/`

`skills-cursor` 是 Cursor 自己同步内置技能（28 个）用的目录，带 `.sync-manifest.json`。写进去会被 Cursor 的同步逻辑覆盖，或者干扰它自己的更新判断。

### 为什么容易错

两个路径只差一个后缀 `-cursor`。任何字符串拼接、前缀匹配、目录遍历都可能误伤。

### 代码落点

```rust
const FORBIDDEN_SUBDIRS: &[&str] = &["skills-cursor", "plugins", "extensions", "agents", "rules"];

fn assert_not_forbidden(target: &Path) -> Result<()> {
    for comp in target.components() {
        if let Some(s) = comp.as_os_str().to_str() {
            if FORBIDDEN_SUBDIRS.contains(&s) {
                bail!("拒绝写入受保护目录: {}", target.display());
            }
        }
    }
    Ok(())
}
```

**注意**：`~/.cursor/rules/` 本机是空的（说明 Cursor 现在用 skills 机制）。但不要往 `rules/` 写——那是给 Cursor Rules 用的，格式不同（是 `.mdc`，不是 `SKILL.md`）。

## R5. 更新检测：规范化哈希，剥离工具回写字段

### 规则

不能对文件原始字节算 hash，必须先规范化。

```
对技能目录下每个文件（递归）:
  1. 排除: .git/, .DS_Store, Thumbs.db, __pycache__/, *.pyc, node_modules/
  2. 排除所有 . 开头的隐藏文件（cc-switch 的做法）
  3. 若为 SKILL.md:
       a. 解析 YAML frontmatter（解析失败则跳过剥离，用原文）
       b. 删除黑名单键:
          enabled_at, installed_at, enabled, last_opened_at,
          last_used_at, cli_version, updated_at, enabled_at_ms
       c. 剩余键按字典序排序后重新序列化
       d. 与 body 重新拼装
  4. 若为文本文件: 换行符统一为 \n（CRLF/LF 差异不算改动）
  5. 计算 sha256(相对路径 + '\0' + 规范化后内容 + '\0')

汇总: 所有文件 hash 以 (相对路径, hash) 排序后拼接，再 sha256
```

### 为什么每一步都不能省

| 步骤 | 不做的后果 | 证据 |
|---|---|---|
| 剥黑名单键 | 千问写 `enabled_at` → 永远显示"已修改" | 本机 `~/.qwenworkcn/skills/dws/SKILL.md` 实测有 `enabled_at: 1787556778796` |
| 排除 `__pycache__` | 跑一遍技能就变"有更新" | cc-switch issue #7772 |
| 排除隐藏文件 | `.claude` 之类的元数据干扰 | cc-switch `collect_files_for_hash` |
| 键排序 | YAML 序列化顺序抖动 | — |
| 换行归一 | Windows CRLF vs git LF → 全员假更新 | xingkongliang/skills-manager CHANGELOG 明确修过 |
| 相对路径入 hash | 改名算不出变化 | — |
| 解析容错 | 本机实测有技能**连 frontmatter 都没有** | `abnormal-hours-approver` |

### 两种哈希，不要混用

cc-switch 区分了两种（这是我们原方案漏掉的）：

| 用途 | 算法 | 特点 |
|---|---|---|
| **更新检测** | 宽松：跳过隐藏文件、`__pycache__`、`*.pyc` | 只关心"内容有没有变" |
| **部署完整性** | 严格：含隐藏文件、空目录、符号链接目标、文件类型 | 判断"用户是不是动过目标目录" |

用途不同：前者比对"远端 vs 本地安装时"，后者比对"目标目录 vs SSOT"。

## R6. 下载安全

内网自产自用风险较低，但如果开放"任何人上传"，这些必须有（cc-switch 全部已实现，直接抄）：

| 防护 | 值 |
|---|---|
| 归档条目数上限 | 30,000 |
| 解压后总字节上限 | 512 MB |
| 压缩体下载上限 | 逐块计数，不信 `Content-Length` |
| 空目录按磁盘块计费 | 4,096 字节/个 |
| 小文件按磁盘块计费 | 4,096 字节/个 |
| symlink 目标长度上限 | 4 KiB |
| 路径穿越 | 解压后每个路径都要 `strip_prefix` 校验 |

## R7. 状态模型：一个技能一条记录

采用 cc-switch 模型，不采用我们原方案的"一条记录 = 技能×工具"：

```sql
CREATE TABLE skills (
    id TEXT PRIMARY KEY,        -- "<host>/<project-path>:<directory>" 或 "local:<directory>"
    name TEXT NOT NULL,
    directory TEXT NOT NULL,
    source_host TEXT,           -- "gitlab.company.com"
    source_path TEXT,           -- "group/sub/skills-repo"
    source_branch TEXT,
    source_subpath TEXT,        -- "skills/销售/sales-report"
    content_hash TEXT,
    installed_at INTEGER,
    updated_at INTEGER,
    enabled_cursor      BOOLEAN DEFAULT 0,
    enabled_claude      BOOLEAN DEFAULT 0,
    enabled_codex       BOOLEAN DEFAULT 0,
    enabled_agents      BOOLEAN DEFAULT 0,
    enabled_qwenwork    BOOLEAN DEFAULT 0,
    enabled_workbuddy   BOOLEAN DEFAULT 0
);
```

**为什么一个技能一条记录**：
- "同一技能装到 3 个工具"是一个概念，不是三条独立事实
- 内容哈希只存一份，不会不一致
- 矩阵表 UI 直接映射（行=技能，列=应用）

**cc-switch 已验证**：`enabled_*` 逐列 `ALTER TABLE ADD COLUMN` 的 migration 模式可行（本机 db 里后 4 列就是这么加的）。
