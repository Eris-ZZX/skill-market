# 内网 Skill 市场 — 设计方案

> 状态：需求已对齐，待评审
> 编写日期：2026-11-13
> 目标读者：决策者（你）、后续开发者

---

## 0. 一句话定位

**公司内网的 Skill 市场。内网 GitLab 是货架，客户端是橱窗和安装器。装哪个、升不升、别人改了你的技能要不要采纳，全部由使用者自己决定。**

这是一个**自助工具**，不是一个**管控工具**。所有设计取舍都服从这一条。

### 明确不做

| 不做 | 原因 |
|---|---|
| 强制版本对齐 / 版本锁定 | 你要的是自选市场，不是 MDM |
| 审批流（客户端内） | 只走 GitLab MR，不自建审批 |
| 使用统计上报 | 自助工具不该有后台台账 |
| "谁装了什么"的中央视图 | 同上 |
| 弹窗催升级 / 定时打扰 | 只在打开应用时显示红点 |
| 下载量 / 评分 / 热度排行 | 无服务端，做不了（见 §6.4） |
| 技能签名 / 供应链审计 | 内网自产自用，暂不需要 |

## 2. 关键调研结论

### 2.1 四个工具的技能目录（已查实）

| 工具 | 用户级目录 | 依据强度 |
|---|---|---|
| **Cursor** | `~/.cursor/skills/` | 官方文档 + 本机存在 |
| **ChatGPT（桌面）** | `~/.agents/skills/` | **官方文档**（与 Codex 共用此目录）；本机无 ChatGPT 客户端，未实测 |
| **千问办公** | `~/.qwenworkcn/skills/` | **官方文档** + 本机存在（13 个技能） |
| **WorkBuddy** | `~/.workbuddy/skills/` | **官方文档** + 本机存在（2 个技能） |

> 注意：本机存在只说明"装了该工具的机器长这样"，**不能**推断同事机器也一定有这个目录。四个工具里同事可能只装了一两个（见 §3.5-1）。

**层级铁律**：必须是 `skills/<技能名>/SKILL.md`，少一层目录就不会被识别。四家一致。

### 2.2 调研发现的四个坑

#### 坑 1：ChatGPT 和 Codex 共用 `~/.agents/skills/`

同一个目录被 ChatGPT 桌面端、Codex CLI、Codex IDE 三方读取。本机该目录有 44 个技能。

- **好处**：省一半工作量，装一次三处生效。
- **代价**：界面上必须文案说明，否则用户会困惑"我只勾了 ChatGPT，为什么 Codex 也有了"。
- **风险**：本机没装 ChatGPT，无法实测。官方文档只写了 "open Skills in the sidebar"，没给路径。第三方整理站说是 `~/.agents/skills/`。
- **对策**：**路径表可配置**，默认填 `.agents/skills/`，装完不生效时引导用户改路径。

#### 坑 2：千问办公会往 `SKILL.md` 里写字段

本机实例：

```yaml
# ~/.qwenworkcn/skills/dws/SKILL.md
---
name: dws
description: 管理钉钉产品能力...
cli_version: ">=1.0.15"
enabled_at: 1787556778796      # ← 千问运行时写入
---
```

**影响**：如果直接用整文件 hash 判断"本地是否被改过"，会永远显示"已修改"。

**对策**：hash 前做**规范化**，剥掉工具回写的易变字段（详见 §7.2）。

#### 坑 3：一个 SKILL.md 要同时喂四个工具

四家能接受的 frontmatter 字段并不相同：

| 字段 | Cursor | ChatGPT/Codex | 千问办公 | WorkBuddy |
|---|---|---|---|---|
| `name` | ✅ | ✅ 必填 | ✅ | ✅ |
| `description` | ✅ | ✅ 必填 | ✅ | ✅ |
| `version` | 忽略 | 忽略 | ✅ 用 | ✅ 用 |
| `metadata:` 嵌套 | ✅ 用 | ✅ 用 | 未见 | 未见 |
| `display_name` | — | — | — | ✅ |
| `summary` / `read_when` | — | — | — | 原生也认 |

**交集只有 `name` + `description`**。

**对策**：我们自己的扩展字段全部收进 `metadata.skillmarket:` 命名空间。这是 `.agents` 生态的既有惯例（本机 44 个技能就是这么写的），而且从语义上明确标出"这是某工具的元数据区"，被忽略是预期行为。

#### 坑 4：分类目录与 tags 是两套事实来源

目录是文件系统位置，tags 是 frontmatter 内容，两者天然会漂移。

**对策**：**不做一一对应，定位分工明确**：
- **目录 = 粗分组**：上架时选一个，改分类要搬家（客户端按 `name` 识别，所以搬家对已装用户无感）
- **tags = 细筛选**：随便打多个，纯检索用
- 上架时把主分类同时写进 `metadata.skillmarket.category`，仅用于展示和校验一致性，不强制同步

**技能身份 = frontmatter 的 `name`，不是路径。** 这是硬规则。索引按 `name` 建，路径只是位置。这样搬家、换分类都不会让已装用户失联。

## 3. 技术选型

### 3.1 你的三条硬指标

1. 发布包尽可能小
2. 兼容性尽可能好
3. 性能尽可能流畅

**关键约束**：内网 + 公司电脑 + 上百台 + 大概率**无外网**。这意味着任何"缺依赖就联网下载"的方案都有风险。

### 3.2 先纠正我上一版的错误

上一版我直接拿**本机**环境（.NET 4.8、WebView2 157、开发者模式开启、Rust/Node 齐全）当成了全公司标准。这是方法错误。查实两条事实：

| 事实 | 出处 | 后果 |
|---|---|---|
| .NET Framework **4.8 只在 Win10 1903 及以后**自带；**1803 / 1809 / LTSC 2019 自带的是 4.7.2** | Microsoft Learn《.NET Framework 系统要求》 | 目标框架若定 4.8，**LTSC 2019 的机器直接起不来**——而 LTSC 恰恰是企业里最常见、最稳定、最不容易升级的那批 |
| WebView2 **在 Win10 上不是系统自带**（只有 Win11 是）。微软明确点名：干净安装的 Win10、Windows Server、**LTSC** 都可能没有 | Microsoft Learn《分发 WebView2 运行时》 | Tauri 方案在 LTSC 上可能装不上 |

第二条还有个更硬的问题：**WebView2 的联网 bootstrapper 只有 2MB，但它必须连微软 CDN 才能下载运行时。内网/气隙环境这条路直接死。** 离线部署只能用 Standalone Installer，**约 150MB** —— 这一个文件就比整个 WPF 方案大 50 倍。

所以"包小"这件事不能只看客户端 exe，要把**前置条件的分发成本**算进去。

### 3.3 候选对比（修正版）

| 方案 | 我方包体 | 运行时前置条件 | 内网可满足性 | 判定 |
|---|---|---|---|---|
| **C# WPF → .NET FW 4.7.2** | **1–3 MB** | 无。Win10 1803+ / Server 2019 **全部自带** | **确定满足，零动作** | ⭐ **推荐** |
| C# WPF → .NET FW 4.8 | 1–3 MB | Win10 1903+ | LTSC 2019 不满足 | ✗ 上一版错误 |
| C# WPF → .NET 8 自包含 | 65–90 MB | 无 | 满足，但包大 30 倍 | 备选 |
| C# WPF → .NET 8 框架依赖 | 2–3 MB | 需装 Desktop Runtime | 需额外分发 ~55MB | ✗ |
| Tauri 2 / Wails | 6–10 MB | **WebView2**（Win10 非自带） | LTSC/Server 未定；离线需 150MB | 备选（须先抽查） |
| Electron | 150–250 MB | 零 | 满足但包大 | ✗ |
| Python + PySide | 40–80 MB | 零 | 满足但包大、启动慢 | ✗ |

**关键判断**：所谓"兼容性最好"，不是比谁的包能在更多系统上跑，而是比**"前置条件在这个内网里有多确定"**。

- WPF 4.7.2 的前置条件是**操作系统版本** —— 我们改不了它，但它早已满足（Win10 1803 是 2018 年的版本）
- Tauri 的前置条件是**一个可能不存在、且内网装不上的运行时**

前者是"确定成立"，后者是"需要抽查 + 可能 150MB 兜底"。差距不在包体大小，在**运维确定性**。

### 3.4 结论：C# + WPF，目标框架 .NET Framework 4.7.2

**为什么是 4.7.2 而不是 4.8**：

| Windows 版本 | 自带 .NET FW |
|---|---|
| Win10 1709 / 1703 | 4.7.1 / 4.7 |
| **Win10 1803 / 1809 / LTSC 2019 / Server 2019** | **4.7.2** ← 最低水位 |
| Win10 1903 ~ 22H2 / Win11 21H2 | 4.8 |
| Win11 22H2 及以后 | 4.8.1 |

.NET Framework 4.x 是**原地更新**（in-place update），向后兼容。所以**目标定 4.7.2，就能在所有 Win10 1803+ 和 Server 2019+ 上跑**，覆盖上表全部行。反之定 4.8，就把 1803/1809/LTSC 2019 全排除了。

**为什么不再往下取 4.7.1 或 4.6.2**：TLS。

- .NET FW **4.7 起**，`ServicePointManager.SecurityProtocol` 默认值是 `SystemDefault`，由操作系统决定 TLS 版本 → 连接内网 GitLab 的 HTTPS 开箱即用
- 4.6.2 及更早，默认不启用 TLS 1.2，必须代码里显式设 `SecurityProtocolType.Tls12`，且容易被后续改动破坏

**4.7.2 是"自带 SystemDefault TLS"和"企业最低水位"的交叉点**，再高就丢兼容性，再低就要自己处理 TLS。

**其余优势**：

- **包大小**：我方程序集 1–3 MB。分发包做成 MSI 或一个文件夹，无需捆绑运行时
- **性能**：WPF 原生渲染，长列表滚动比 WebView 顺。内存 ~60–90 MB
- **部署**：拷过去就能跑，不需要管理员

**代价（必须接受）**：

- 语言版本受限：**C# 7.3 是安全基线**。用 SDK 风格工程 + polyfill（`IsExternalInit`）可以上到 C# 9 左右，但别指望 C# 12 的新语法
- 做不了"真正的单文件 exe"（除非 ILMerge / Costura 合并），实际交付是 exe + 几个 dll 的文件夹，或打成 MSI
- XAML 写卡片布局比 HTML/CSS 啰嗦，UI 开发效率低于 Web 技术栈
- 第三方控件生态偏老，建议用 [WPF-UI](https://github.com/lepoco/wpfui) 或 HandyControl 补现代感

### 3.5 其他兼容性风险（比运行时更可能真的绊倒你）

运行时只是第一关。真正在百台公司机器上出事的地方，通常是这些：

| # | 风险 | 为什么会发生 | 对策 |
|---|---|---|---|
| 1 | **工具本身没装** | 同事没装千问办公 / WorkBuddy，对应的 skills 目录**根本不存在** | 启动时逐个探测工具目录，不存在则显示"未安装"，**不自动创建**、不报错。安装目标只列已探测到的工具 |
| 2 | **`%USERPROFILE%` 被 OneDrive 重定向** | 很多公司开了 OneDrive 文件夹备份，`~/.cursor/skills` 落在 OneDrive 里 → 同步冲突、按需文件是占位符读不到 | 启动时检测：路径含 `OneDrive` 则警告，并允许把技能库放到本地盘 |
| 3 | **内网 GitLab 用自签证书** | 内网自建 GitLab 极其常见，`HttpClient` 默认拒绝 | **不要用 `ServerCertificateValidationCallback` 无条件返回 true**（那是安全漏洞）。正确做法：首次连接失败时提示用户，允许其把该 CA 证书导入 Windows 受信任根，提供一键导入按钮 |
| 4 | **企业 SSL 解密代理（MITM）** | 代理替换证书，同样触发证书错误 | 同上：走系统信任链，让用户/IT 导入企业根证书 |
| 5 | **杀软 / EDR 拦截未签名 exe** | 公司电脑常见。首次运行被拦或直接删除 | 尽量做代码签名；否则提前找 IT 加白名单。**这个必须在 M0 就去问，不能等到发版** |
| 6 | **长路径超 260 字符** | 技能目录嵌套深 + 中文路径 | 统一用 `\\?\` 前缀访问；或在 manifest 声明 `longPathAware` |
| 7 | **32 位系统** | LTSC 有 x86 版 | 编 AnyCPU，或在 manifest 明确要求 x64 并在启动时检查 |
| 8 | **中文分类目录在 URL 里** | `skills/销售/xxx` 需 URL 编码 | 所有路径参数统一 `Uri.EscapeDataString`，且注意 GitLab 要求**整段 path 编码**（斜杠编成 `%2F`）。M0 阶段先手工验证一次 API |
| 9 | **Windows Defender 受控文件夹访问** | 企业策略可能禁止往某些目录写 | 安装失败时给出明确文案，并提示路径可配置 |

**其中第 1 条最重要**：这不是"异常处理"，而是**产品主流程的一部分**。四个工具里同事可能只装了其中一两个，客户端必须优雅降级——只对已安装的工具提供安装选项。

### 3.6 如果团队更熟 JS/TS，什么情况下改走 Tauri 2

不改。默认走 WPF。**除非**满足全部三条：

1. 你/团队对 C# 完全不熟，且对 XAML 有明显抗拒
2. 抽查 10 台以上真实同事机器，**100% 有 WebView2**
3. 接受把 WebView2 Standalone Installer（~150MB）放进内网共享盘作为兜底

抽查命令见附录 D。如果三条都满足，Tauri 可行，包 6–10MB，UI 用 HTML/CSS 做"市场感"确实更快。

**架构不受影响**：仓库规范、API 清单、hash 算法、四状态判定、发布流程在两种方案下完全一致，只有表现层换掉。所以这个决策可以晚做，不阻塞 M0。

## 4. 系统架构

### 4.1 全局形态

```
┌─────────────────────────────────────────┐
│  内网 GitLab（唯一后端）                  │
│  ├── skills/<分类>/<技能名>/SKILL.md      │
│  ├── skills/.../scripts/ ...             │
│  ├── .gitlab-ci.yml   （轻校验）          │
│  └── Releases         （客户端自身安装包）  │
└─────────────────────────────────────────┘
              ↑ REST API（HTTPS）
              │  读：公开/内部可见
              │  写：共享 token + 保护分支
┌─────────────────────────────────────────┐
│  桌面客户端（每台电脑）                    │
│  ├── 市场页 / 详情页 / 我的技能 / 发布页    │
│  ├── 本地状态库 state.json               │
│  ├── 本地缓存（仓库 zip + 解析结果）        │
│  └── 部署引擎（复制 / junction 可选）        │
└─────────────────────────────────────────┘
              ↓ 文件系统
   ~/.cursor/skills/   ~/.agents/skills/
   ~/.qwenworkcn/skills/   ~/.workbuddy/skills/
```

**零服务端**。没有数据库、没有后台进程、没有运维对象。所有状态在这台电脑的 `%APPDATA%\SkillMarket\` 里。

### 4.2 为什么不需要 clone 仓库

这是本次调研最重要的发现：GitLab 支持

```
GET /api/v4/projects/:id/repository/archive.zip?path=skills/销售/report&sha=<commit_sha>
```

**只下载指定子目录的 zip**。因此：

| 操作 | 请求数 | 说明 |
|---|---|---|
| 打开应用（无变化） | **1** | 只查 head commit |
| 打开应用（有变化） | **2** | 再下一次整仓 zip，本地解析全部技能 |
| 安装单个技能 | **1**（缓存新鲜时 0） | 直接用缓存的 zip 内容 |
| 检查更新 | **1** | 同上 |

对比 git 方案：要装 Git for Windows、要 clone、要处理凭据、要处理代理、要处理大仓库。**全部省掉。**

而且因为整仓 zip 是一次性拉下来的，**N 个技能的更新检测只花 2 个请求**，不是 N 个。这在百人规模下对 GitLab 极其友好。

## 5. 仓库规范

### 5.1 目录结构

```
skill-repo/
├── README.md                    # 使用说明（给人看）
├── .gitlab-ci.yml               # 轻量校验（见 §5.5）
└── skills/
    ├── 销售/
    │   ├── sales-report/
    │   │   ├── SKILL.md
    │   │   ├── scripts/
    │   │   └── references/
    │   └── customer-visit/
    │       └── SKILL.md
    ├── 研发/
    │   └── code-review/
    │       └── SKILL.md
    └── 通用/
        └── meeting-notes/
            └── SKILL.md
```

**规则**：
- 技能目录名 = frontmatter 的 `name`（强制，CI 校验）
- `name` 全仓库唯一（跨分类也不能重名，因为四家工具都要求技能名唯一）
- 分类目录名中文可接受（GitLab 和 Windows 都支持 UTF-8 路径）
- 单个技能体积建议 < 5 MB（详见 §8.3）

### 5.2 SKILL.md 契约

```yaml
---
name: sales-report                    # 必填。唯一标识。小写字母、数字、连字符
description: >                        # 必填。四家工具唯一的共同必填项
  生成销售周报，包含同比环比与异常波动提示。
  当用户提到销售周报、业绩报表、月度汇总时使用。
version: 1.2.0                        # 建议。仅用于展示，不作为更新判据
metadata:                             # 我方扩展全部放这里（生态惯例，工具会忽略）
  skillmarket:
    category: 销售                     # 与所在目录一致，仅用于展示
    tags: [销售, 报表, 周报]            # 细筛选用
    authors: ["张三/工号1234"]          # 发布时自动写入
    owner_gitlab: zhangsan            # 原作者的 GitLab 用户名 → 用于 MR 自动指派
---
```

**为什么扩展字段放 `metadata.skillmarket`**：
1. `.agents` 生态的既有惯例（本机 44 个技能都这么写）
2. 语义上明确是"元数据区"，被工具忽略是预期行为
3. 顶层只留 `name` / `description` / `version` 三个四家都能容忍的键

### 5.3 分支与权限

| 配置 | 值 | 原因 |
|---|---|---|
| 可见性 | **Internal**（登录可见） | 不完全公开，但公司内全员可读 |
| `main` | **保护分支**，禁止直推 | 所有变更强制走 MR |
| 允许合并 | Maintainer | 人工审核，这就是"审批流"，不用另做 |
| 共享 token | **Project Access Token**，角色 Developer，scope 仅 `api` | 能推分支、能提 MR、**不能推 main** |

### 5.4 共享 token 的风险与对策（重要）

你选了内置共享 token。我按你的选择做，但必须明确代价：

**风险 1：token 在客户端里 = 人人可获取。** 编译进 exe 只是混淆，不是加密，反编译就能取出来。任何员工都能拿到一个能推分支的凭据。

**对策（必须全做）**：
1. token **只授这一个项目**，scope 只给 `api`，不给 `write_repository` 之外的能力
2. `main` 保护 → token 不能直推主干，只能推分支 + 提 MR，**破坏面被限制在"能提一堆 MR"**
3. token **设过期时间**（建议 6 个月），换发时同步发新版客户端
4. 仓库只存技能文本，不放任何敏感配置、密钥、内部文档
5. 出问题时的止损路径：吊销 token → 已装客户端全部失去读写能力 → 发新版。要接受"止血有延迟"

**风险 2：所有 MR 的作者都是同一个机器人账号。** 这直接削弱你要的"对自己上传的进行更新"。

**对策**：身份靠**声明**而非鉴权，三处留痕：
1. commit message 前缀带 `[发布人: 张三/1234]`
2. MR 描述里列出发布人、技能、变更摘要
3. `metadata.skillmarket.authors` 写入作者
4. **MR 自动指派给该技能的 `owner_gitlab`** —— 这是"自己更新自己的技能"最自然的流转方式，新 MR 直接落到原作者面前等着 review

> 如果日后觉得共享 token 太糙，升级路径很清晰：改为**每个员工填自己的 PAT**，代码改动只在"凭据获取"这一层，其余不变。所以现在不必纠结。

### 5.5 CI 轻校验（可选但建议）

`.gitlab-ci.yml` 只做三件事，不做构建：

```yaml
validate:
  script:
    - 每个 SKILL.md 必须有 name + description
    - name 必须小写字母数字连字符
    - name 必须等于所在目录名
    - 全仓库 name 不得重复
    - 禁止提交 .env / *.key / *.pem
```

这样能拦住 90% 的低级错误，且 MR 页面直接显示红叉，比客户端校验更可信。

## 6. 客户端设计

### 6.1 五个页面

| 页面 | 内容 |
|---|---|
| **市场** | 左侧分类栏 + 顶部搜索框 + 卡片网格。卡片显示：名称、描述前两行、分类、tags、version、更新时间、状态徽章（已安装/可更新） |
| **技能详情** | 渲染后的 `SKILL.md` 正文 + 元信息面板 + 更新历史（最近 5 次 commit）+ 安装按钮组（按工具勾选） |
| **我的技能** | 已安装清单。两种视角切换：按技能分组 / 按工具分组。每行显示当前版本、工具、状态徽章、操作（更新/卸载/查看来源） |
| **发布** | 选本地目录 → 自动解析 → 预览将提交的文件 → 填分类/tags → 提交 MR → 打开浏览器 |
| **设置** | GitLab 地址/项目、共享 token（只读显示，可覆盖）、工具路径表、复制/junction 开关、代理、检查更新频率 |

### 6.2 读操作的鉴权策略（关键细节）

因为仓库是 **Internal** 而非 Public，匿名 API 读会失败。但共享 token 存在"过期就全挂"的风险。

**策略**：**先匿名请求，失败再带 token 重试**。

```
GET /projects/:id  （无 token）
  ├─ 200 → 仓库是 Public，全程匿名读，token 只用于写
  └─ 401/404 → 带共享 token 重试 → 成功则记住该模式
```

好处：如果哪天仓库改成 Public，客户端**零改动**就获得"读不依赖 token"的健壮性。

### 6.3 部署引擎

安装一个技能到某工具，执行：

1. 目标路径 = `<工具根目录>/skills/<name>/`
2. **若目标已存在**：
   - 是本应用装的、且内容未改 → 直接覆盖
   - 是本应用装的、但内容改了 → 提示"该技能在此工具下已被修改，覆盖会丢失改动"，需确认
   - 不是本应用装的（用户自己放的）→ **拒绝**，提示"已存在同名技能，非本应用安装，请先手动处理"
3. **复制模式**（默认）：整目录递归拷贝
4. **junction 模式**（高级选项）：`mklink /J`，源目录是本地库 `%APPDATA%\SkillMarket\library\<name>`
5. 记录到 `state.json`

**已实测**：本机 junction 和目录软链**都不需要管理员权限**创建成功。

**为什么不把状态文件写在技能目录里**：某些工具可能对目录内的额外文件敏感。所有状态集中存在 `%APPDATA%\SkillMarket\state.json`，技能目录保持干净。

**扫描发现**：启动时扫描四个工具目录，把非本应用管理的技能也列出来（标为"本地"），让用户看得到全貌，但不接管。

### 6.4 关于"市场感"的诚实说明

你选了用 GitLab 原生能力兼职做市场数据。**能做到 / 做不到**：

| 能做到 | 做不到 |
|---|---|
| 最近更新时间（commit 时间）✅ | 下载量 ❌ |
| 作者（commit author / frontmatter）✅ | 评分 ❌ |
| 变更历史（commit 列表）✅ | 收藏 ❌ |
| 分类 + tags 筛选 ✅ | 热度排行 ❌ |
| 全文搜索（本地索引）✅ | "多少人在用" ❌ |

所以"市场"的感觉靠**卡片视觉、分类导航、搜索、详情预览**撑起来，不靠榜单。

如果日后确实需要热度，最小代价方案：在仓库里放一个 `stats.json`，由 CI 定时汇总某个汇总源（比如 GitLab 的 Issue 👍），或者引入一个极轻量的服务端。**现在不做。**

### 6.5 客户端自身更新

- 安装包作为 GitLab **Release asset** 上传到同一个项目
- 客户端启动时查 `GET /projects/:id/releases?per_page=1`，比对 tag
- 有新版本 → 设置页显示"有新版本"，点一下下载安装包（用户自己装，不静默升级）

## 7. 核心机制

### 7.1 数据存储

`%APPDATA%\SkillMarket\`

```
state.json            # 已安装清单（核心）
cache\
  repo.zip            # 最近一次拉取的整仓快照
  head.json           # { sha, fetched_at }
  index.json          # 解析后的技能索引
library\              # junction 模式的本地库
logs\                 # 操作日志（滚动 7 天）
```

`state.json` 结构：

```json
{
  "schemaVersion": 1,
  "gitlab": { "baseUrl": "...", "projectPath": "...", "authMode": "token" },
  "installs": [
    {
      "name": "sales-report",
      "tool": "cursor",
      "targetPath": "C:\\Users\\x\\.cursor\\skills\\sales-report",
      "mode": "copy",
      "installedHash": "sha256:...",
      "installedVersion": "1.2.0",
      "sourceCommit": "a1b2c3d...",
      "sourcePath": "skills/销售/sales-report",
      "installedAt": "2026-11-13T09:00:00Z"
    }
  ]
}
```

**一条 `installs` 记录 = 一个技能装在一个工具里**。同一技能装到三个工具就是三条记录，各自独立判断更新和本地修改。

### 7.2 规范化内容 hash（更新判定的核心）

这是整个方案里最需要精确实现的部分。**不能直接用整文件 hash。**

算法：

```
对技能目录下每个文件（递归）:
  1. 排除: .git/, .DS_Store, Thumbs.db, node_modules/, __pycache__/
  2. 若为 SKILL.md:
       a. 解析 YAML frontmatter
       b. 删除黑名单键（工具回写的易变字段）:
          enabled_at, installed_at, enabled, last_opened_at,
          last_used_at, cli_version, updated_at
       c. 剩余键**按字典序排序**后重新序列化
       d. 与 body 重新拼装
  3. 若为文本文件: 换行符统一为 \n（CRLF/LF 差异不算改动）
  4. 计算 sha256(相对路径 + '\0' + 规范化后内容)

汇总: 所有文件 hash 按相对路径字典序排序后拼接，再 sha256
```

**为什么每一步都不能省**：

| 步骤 | 不做的后果 |
|---|---|
| 排除黑名单键 | 千问写 `enabled_at` → 永远显示"已修改" |
| 键排序 | YAML 序列化顺序抖动 → 假更新 |
| 换行归一 | Windows CRLF vs git LF → 全员假更新 |
| 相对路径入 hash | 改名算不出变化 |

> 调研中看到 `xingkongliang/skills-manager` 的 CHANGELOG 明确修过一个 bug：*"只差行尾也不再让技能显示为待更新"* —— 说明这个坑真实存在且很常见。

### 7.3 四种状态

界面只说这四句话，不多说：

| 状态 | 本地 hash | 远端 hash | 界面表现 |
|---|---|---|---|
| **最新** | = | = | 无标记 |
| **可更新** | = | ≠（远端新） | 蓝色「更新」按钮 |
| **已修改** | ≠（本地改） | = 安装时 | 灰色「已修改」标记，不提示更新 |
| **冲突** | ≠（本地改） | ≠ 安装时 | 黄色标记 + 三选一 |

**冲突时三个选项**：

| 选项 | 行为 |
|---|---|
| 留我的 | 不动本地，记录"用户已忽略此次更新"，下次远端再变时重新提示 |
| 用远端 | 覆盖本地（先备份到 `logs\backup\`） |
| 另存一份 | 本地改名成 `<name>-local`，再装新版 `<name>` |

### 7.4 更新判定的完整流程

```
1. GET /projects/:id/repository/commits?per_page=1  → head SHA
2. 与 cache/head.json 比对
   ├─ 相同 → 缓存有效，直接用 index.json，结束（1 个请求）
   └─ 不同 → 下载 archive.zip 整仓 → 解析 → 重算每个技能 hash → 写 index.json
3. 对每条 install 记录:
   normalizedHash(本地目标目录) vs index[name].hash
   ├─ 本地 == installedHash 且 远端 != installedHash → 可更新
   ├─ 本地 != installedHash 且 远端 == installedHash → 已修改
   ├─ 本地 != installedHash 且 远端 != installedHash → 冲突
   └─ 其他 → 最新
```

**为什么把 `version` 排除在判据之外**：一定会有人忘改版本号。`version` 只用于展示 `v1.2 → v1.3`。若内容变了但 `version` 没变，仍提示可更新，并附注「版本号未更新」，提醒发布者补上。

**为什么不用 commit SHA 作为判据**：仓库里任何技能一改，整仓 head SHA 就变。如果按 head SHA 判断，所有技能都会显示"可更新"。必须按**技能自身目录内容**算，这就是 §7.2 那套 hash。

### 7.5 发布流程

```
1. 用户选本地技能目录（或从"我的技能"里选一个已装的）
2. 校验:
   - name 合法、description 非空、name == 目录名
   - 无 .env / *.key / *.pem / 超大文件
   - 目标 name 是否已被别人占用（若占用且 owner 不是自己 → 明确提示）
3. 补全 frontmatter: version（沿用或自增）、authors、owner_gitlab
4. POST /repository/branches            建 release/<name>-<时间戳>
5. POST /repository/commits             批量提交所有文件（base64 编码二进制）
6. POST /merge_requests                 建 MR，assignee = 原 owner_gitlab
7. 弹窗显示 MR 链接 + "复制链接"
```

**请求体注意**：GitLab 18.4.6 起，`POST /repository/commits` 只从 JSON body 读参数，**放在 query string 会 400**。必须全部走 body。

## 8. GitLab API 清单

全部走 `{baseUrl}/api/v4`。

| 用途 | 方法 | 端点 |
|---|---|---|
| 项目信息 | GET | `/projects/{urlencoded_path}` |
| 仓库树 | GET | `/projects/{id}/repository/tree?recursive=true&ref=main` |
| 单文件原文 | GET | `/projects/{id}/repository/files/{urlencoded_path}/raw?ref={sha}` |
| **整仓 zip** | GET | `/projects/{id}/repository/archive.zip?sha={sha}` |
| **单技能 zip** | GET | `/projects/{id}/repository/archive.zip?path={subpath}&sha={sha}` |
| head commit | GET | `/projects/{id}/repository/commits?per_page=1` |
| 技能历史 | GET | `/projects/{id}/repository/commits?path={subpath}&per_page=10` |
| 建分支 | POST | `/projects/{id}/repository/branches` |
| 批量提交 | POST | `/projects/{id}/repository/commits` |
| 建 MR | POST | `/projects/{id}/merge_requests` |
| 最新 Release | GET | `/projects/{id}/releases?per_page=1` |

**版本要求**：`archive?path=` 参数需 GitLab **13.x+**（2020 年后版本都有）。`GET /releases` 需 11.7+。内网 GitLab 版本号需确认（见 §13）。

## 12. 与开源项目的对比定位

调研过 GitHub 同类项目，结论：**没有直接可用的**。

| 项目 | Stars | 为什么不能直接用 |
|---|---|---|
| [xingkongliang/skills-manager](https://github.com/xingkongliang/skills-manager) | 7.5k | Rust/Tauri 双栈；子目录解析正则**只认 `github.com/tree/`**；市场走 skills.sh；自更新写死 `api.github.com`。Fork 需长期维护大 diff |
| [qufei1993/skills-hub](https://github.com/qufei1993/skills-hub) | 1.9k | GitLab 侧 API 写死 `gitlab.com/api/v4`，浏览器授权要自建 OAuth 应用 |
| [jiweiyeah/Skills-Manager](https://github.com/jiweiyeah/Skills-Manager) | 1.1k | 无 GitLab 相关代码；Windows junction 降级策略可参考，但项目 9 月后停更 |
| [shenysun/skills-manager](https://github.com/shenysun/skills-manager) | 243 | 更新锚点设计（子目录 tree SHA）值得借鉴，与我们思路一致 |
| [luongnv89/asm](https://github.com/luongnv89/asm) | 974 | CLI/TUI，GitHub + 自带 registry 中心 |

**共性缺口**：没人把内网 GitLab 做成一等公民，没人解决"应用如何在内网分发"，也没人做"自选更新、不强制"的定位。

**可借鉴的具体点**（MIT/ISC 许可，可直接抄思路）：

## 附录 A：为什么不用 SQLite

安装清单的规模是"每人几十个技能、几百条记录"。JSON 文件 + 原子写入（写临时文件后 `File.Replace`）完全够用，且：

- 零额外依赖（SQLite 要带 native dll，破坏"单 exe"目标）
- 人工可读、可编辑、可 diff、易排障
- 出问题让员工发一份 `state.json` 过来就能定位

等到记录数上千再考虑迁移，接口层先抽好即可。

## 附录 B：Windows 路径与权限

| 操作 | 需要管理员？ | 说明 |
|---|---|---|
| `mklink /J`（junction） | **不需要** | 普通账户即可。**但不代表在所有机器上都可靠**：部分企业安全策略会限制 reparse point 创建，需运行时探测 |
| `mklink /D`（目录软链） | 需要，除非开启开发者模式 | **开发者模式默认关闭**，不能假设同事机器已开。本机测试成功是因为本机已开启 |
| 文件复制 | 不需要 | 唯一零风险路径 |

**结论：默认 copy。** junction 作为"高级选项"，且必须在**运行时探测**（试着建一个临时 junction，成功才在 UI 中显示该选项），而不是根据"本机测试通过"就认为全局可用。软链不作为选项。

## 附录 C：状态徽章的视觉规范

只有四种状态，颜色和文案固定，不要扩展：

| 状态 | 颜色 | 文案 | 位置 |
|---|---|---|---|
| 最新 | 无 | （不显示） | — |
| 可更新 | 蓝 `#2563EB` | 更新 | 卡片右上角 + 列表操作列 |
| 已修改 | 灰 `#6B7280` | 已修改 | 卡片右上角 |
| 冲突 | 黄 `#D97706` | 需处理 | 卡片右上角 + "我的技能"置顶 |

全局只有一个红点：**"我的技能"侧边栏入口**，表示有可更新或待处理项。不弹窗、不托盘气泡、不发通知。

## 附录 D：环境核查脚本

**不要用开发机的环境代表全公司。** 在真实同事机器上跑这个脚本，收集 10 台以上样本，再定最终参数。

```powershell
# ===== 请在一台【同事的日常办公机】上运行 =====
Write-Output "===== 1. 系统版本 ====="
$os = Get-CimInstance Win32_OperatingSystem
Write-Output "Caption : $($os.Caption)"
Write-Output "Version : $($os.Version)"
Write-Output "Build   : $((Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows NT\CurrentVersion').CurrentBuild)"

Write-Output "`n===== 2. .NET Framework 版本 ====="
$rel = (Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full' -EA SilentlyContinue).Release
$fw = if ($rel -ge 533320) { '4.8.1' } elseif ($rel -ge 528040) { '4.8' }
      elseif ($rel -ge 461808) { '4.7.2' } elseif ($rel -ge 461308) { '4.7.1' }
      elseif ($rel -ge 460798) { '4.7' }  elseif ($rel -ge 394802) { '4.6.2' }
      else { "未知(Release=$rel)" }
Write-Output "Release : $rel"
Write-Output "版本    : $fw"

Write-Output "`n===== 3. WebView2 运行时 ====="
$wv = (Get-ItemProperty 'HKLM:\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}' -EA SilentlyContinue).pv

if ($wv)      { Write-Output "已安装(机器级): $wv" }
elseif ($wvU) { Write-Output "已安装(用户级): $wvU" }
else          { Write-Output "未安装 —— Tauri/Wails 方案不可用，需离线安装包(~150MB)" }

Write-Output "`n===== 4. 四个 AI 工具的技能目录 ====="
$dirs = @{
  'Cursor'      = "$env:USERPROFILE\.cursor\skills"
  'ChatGPT/Codex' = "$env:USERPROFILE\.agents\skills"
  '千问办公'     = "$env:USERPROFILE\.qwenworkcn\skills"
  'WorkBuddy'   = "$env:USERPROFILE\.workbuddy\skills"
}
foreach ($k in $dirs.Keys) {
  $p = $dirs[$k]
  if (Test-Path $p) {
    $n = (Get-ChildItem $p -Directory -EA SilentlyContinue).Count
    Write-Output "$k : 存在 ($n 个技能)  $p"

Write-Output "`n===== 5. 用户目录是否被 OneDrive 重定向 ====="

}

Write-Output "`n===== 6. junction 能否创建（无需管理员）====="
$tmpA = Join-Path $env:TEMP "sm_probe_src_$(Get-Random)"
$tmpB = Join-Path $env:TEMP "sm_probe_lnk_$(Get-Random)"
try {
  New-Item -ItemType Directory -Force -Path $tmpA | Out-Null
  $r = cmd /c mklink /J "$tmpB" "$tmpA" 2>&1
  if (Test-Path $tmpB) { Write-Output "junction : 可用"; cmd /c rmdir "$tmpB" | Out-Null }
  else { Write-Output "junction : 不可用 -> $r" }
} catch { Write-Output "junction : 异常 -> $_" }
finally { Remove-Item -Recurse -Force $tmpA -EA SilentlyContinue }

Write-Output "`n===== 7. 内网 GitLab 可达性 & 证书 ====="

try {

Write-Output "`n===== 8. 长路径支持 ====="
```

### 解读要点

| 检查项 | 结论 |
|---|---|
| #2 全部 ≥ 461808（4.7.2） | 目标框架定 4.7.2，方案不变 |
| #2 有机器 < 4.7.2 | 降到 4.6.2，且必须显式设 TLS 1.2（见 §3.4） |
| #3 全部有 WebView2 | Tauri 才进入候选（还要看 §3.6 另两条） |
| #3 有机器没有 | 走 WPF，别再考虑 Tauri |
| #4 某个工具不存在 | 该工具作为"未安装"处理，产品主流程要优雅降级（§3.5-1） |
| #5 命中 OneDrive | 技能库默认放本地盘，不能让状态和技能落在同步目录 |
| #6 junction 不可用 | 隐藏高级选项，只提供 copy |
| #7 证书报错 | 走 CA 导入流程，禁止无条件跳过校验（§3.5-3） |
| #8 LongPathsEnabled=0 | 必须自己加 `\\?\` 前缀处理长路径 |

**建议取样**：不少于 10 台，且必须覆盖不同部门、不同年份采购的机器。只测开发同事的机器没有意义——他们的环境本来就最齐全。
