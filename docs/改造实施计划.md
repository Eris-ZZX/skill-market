### 1.2 抽象设计

```rust
/// 仓库坐标（provider 无关）
pub struct RepoRef {
    pub host: String,        // "gitlab.company.com"
    pub path: String,        // "group/sub/skills-repo"（GitLab 支持子组）
    pub branch: String,
}

pub trait GitProvider: Send + Sync {
    /// 归档下载 URL
    fn archive_url(&self, repo: &RepoRef, path: Option<&str>) -> Result<Url>;

    /// 出口断言：URL 拼好后验证落点未被改写
    fn assert_archive_url(&self, url: &Url, repo: &RepoRef) -> Result<()>;

    /// 需要带的认证头
    fn auth_headers(&self) -> Vec<(String, String)>;

    /// 归档解压后是否需要剥离一层根目录
    fn has_root_prefix(&self) -> bool;
}
```

### 1.3 GitLab 实现要点

**归档 URL**：

```
{scheme}://{host}/api/v4/projects/{urlencoded_path}/repository/archive.zip
  ?sha={branch}                      // 分支或 tag 或 commit
  &path={subpath}                    // ← 可选，只下子目录
```

**关键差异 —— GitLab 更省**：

| | GitHub | GitLab |
|---|---|---|
| 单技能下载 | 只能整仓（`archive/refs/heads/{b}.zip`） | **可指定 `path=` 只下子目录** |
| 认证 | 匿名或 token | 匿名或 `PRIVATE-TOKEN` / `JOB-TOKEN` |

这直接解决了我们方案 §4.2 提到的问题：GitHub 上装一个技能要下整个仓库，GitLab 只下那个目录。

**URL 编码（关键陷阱）**：

GitLab 要求 `project_id` 位置放**整段路径 URL 编码**，斜杠要编成 `%2F`：

```
group/sub/skills-repo  →  group%2Fsub%2Fskills-repo
```

不是 `group/sub/skills-repo`（会被当成三段路径）。这一点必须写测试。

**出口断言（GitLab 版）**：

```rust
fn assert_archive_url(&self, url: &Url, repo: &RepoRef) -> Result<()> {
    // 1. scheme 必须 https（内网自签证书也要 https，不降级 http）
    // 2. host 必须等于配置的 host（精确匹配，不做后缀匹配）
    // 3. path 必须以 /api/v4/projects/{encoded_path}/repository/archive 开头
    // 4. query 里不能有 sha/path 之外的意外参数（防注入 path=../../）
}
```

**sha/path 参数的注入防护**：

GitLab 的 `path=` 参数如果被注入 `..`，会下到仓库外吗？**不会** —— GitLab 侧会校验。但我们仍要在客户端再校验一遍（纵深防御）：

```rust
fn assert_safe_subpath(p: &str) -> Result<()> {
    if p.split('/').any(|s| s == ".." || s == "." || s.is_empty()) {
        bail!("非法子路径: {p}");
    }
    Ok(())
}
```

### 1.4 解压根目录的差异

| Provider | 归档结构 |
|---|---|
| GitHub | `repo-branch/...`（固定一层） |
| GitLab（整仓） | `repo-branch-sha/...`（一层，含 sha） |
| GitLab（`path=` 子目录） | `repo-branch-sha/sub/path/...`（**仍带完整根**） |

**注意**：GitLab 用 `path=` 时，归档里**仍然带完整的 `repo-branch-sha/` 前缀**，只是内容只有那个子目录。所以剥离一层根目录的逻辑通用，但要按"第一个路径段"剥，不能硬编码 `{repo}-{branch}`。

cc-switch 现在的剥离逻辑（4351 行附近）需要改成"剥第一层，不管它叫什么"。

### 1.5 保留 GitHub 支持

不要删掉 GitHub provider —— 保留它可以：
- 继续用现成的公共技能仓库（作为补充源）
- 便于对照测试（同一技能在两个 provider 下行为一致）

只是**默认仓库改成 GitLab**。

## 3. 工具目录探测（R1 落地）

### 3.1 现状问题

`get_app_skills_dir()` 只返回路径，不判断存在性。上层（`sync_to_app_dir`、`preflight_install_destination`）直接 `create_dir_all`。

### 3.2 改造

新增探测层，**不改** `get_app_skills_dir` 的签名（避免大面积改动），而是增加：

```rust
pub struct ToolDetection {
    pub kind: AppType,
    pub root_dir: PathBuf,
    pub root_exists: bool,
    pub skills_dir: PathBuf,
    pub skills_dir_exists: bool,
}

impl SkillService {
    /// 只读，不创建任何东西
    pub fn detect_all_tools() -> Vec<ToolDetection> { ... }

    /// 安装前置检查：根目录必须存在
    fn assert_tool_installed(det: &ToolDetection) -> Result<()> {
        if !det.root_exists {
            bail!("{} 未安装（{} 不存在）", det.kind.display_name(), det.root_dir.display());
        }
        Ok(())
    }
}
```

**调用点**：所有 `create_dir_all` 之前加 `assert_tool_installed`。

### 3.3 UI 影响

前端「安装到」的应用列表，数据源从"全部支持的应用"改成 `detect_all_tools()` 里 `root_exists == true` 的。

这对应 cc-switch 前端 `useSkillInstallTargets` 里的 `visibleAppIds` 逻辑 —— 它已经有"只显示可见应用"的概念，只是数据来源要换成探测结果。

## 5. Cursor 目录保护（R4 落地）

### 5.1 硬编码排除

```rust
/// 这些子目录绝不允许写入（属于工具自身管理）
const FORBIDDEN_DIR_NAMES: &[&str] = &[
    "skills-cursor",   // Cursor 内置技能同步目录
    "plugins",
    "extensions",
    "rules",
    "agents",
];

fn assert_writable_target(target: &Path) -> Result<()> {
    for comp in target.components() {
        if let Component::Normal(s) = comp {
            if let Some(name) = s.to_str() {
                if FORBIDDEN_DIR_NAMES.contains(&name) {
                    bail!("拒绝写入受保护目录: {}", target.display());
                }
            }
        }
    }
    Ok(())
}
```

### 5.2 调用点

- `sync_to_app_dir` 入口
- `preflight_install_destination`
- `remove_from_app`（删除也要保护）
- 迁移/备份恢复

## 6. 内网适配

### 6.1 WebView2（必须）

**现状**：`tauri.conf.json` 未配 `webviewInstallMode`，默认 `downloadBootstrapper`（联网）。

**改法**（二选一）：

**A. 内嵌离线包**

```json
{
  "bundle": {
    "windows": {
      "webviewInstallMode": {
        "type": "offlineInstaller",
        "silent": true
      }
    }
  }
}
```

代价：安装包 +150 MB。

**B. 内网共享盘兜底**

保持 `downloadBootstrapper`，但把离线安装包放共享盘，安装器失败时提示用户手动装。

代价：安装包小，但首装可能失败，需要 IT 配合。

**推荐 A**。150 MB 在内网共享盘分发不是问题，但省掉一类支持工单。

### 6.2 关闭 GitHub 相关功能

| 功能 | 位置 | 处理 |
|---|---|---|
| skills.sh 市场 | `skills_sh_*` 函数、`SkillsShApiResponse` | 关闭或移除 UI 入口 |
| GitHub 登录 | `git_backup.rs`、`github_api.rs` | 移除或替换为 GitLab |
| 自更新检查 | `tauri.conf.json` 的 `plugins.updater.endpoints` | 改为内网 GitLab Releases |
| 遥测 | 检索有无 | 确认无 |

**updater 改动**：

```json
"endpoints": [
  "https://gitlab.company.com/api/v4/projects/<id>/releases/permalink/latest/download/latest.json"
]
```

注意：GitLab 的 Releases API 结构和 Tauri updater 期望的 `latest.json` 格式不同，需要自己生成这个文件并作为 release asset 上传。

### 6.3 证书

自签证书场景，**绝不** `danger_accept_invalid_certs(true)`。正确做法：

1. 首次连接失败 → 提示"无法验证服务器证书"
2. 提供"为什么"说明（可能是自签或企业代理）
3. 引导把 CA 证书导入 Windows 受信任根（提供按钮打开 `certmgr.msc` 或直接调 API 导入）
4. 导入后重试
